## 背景・目的

Web UI は Pocket（スマートフォン向け棚）の状態を、ページを開いたとき、タブに戻ったとき、アップロードや削除や分離の完了時、手動の「状態を再読込」で取り直す。棚状態の取得は曲ごとに Pocket へ問い合わせるため、曲数が多いと 1 回に数十秒かかる。タブを切り替えて戻るたびに取り直しが走り、確認中の表示（ボタンのスピナーと経過秒）が頻繁に出て煩わしい。また、確認中に別の契機が重なると要求が並列に飛ぶ。

この変更で、タブ復帰では棚状態を取り直さず（曲一覧とジョブだけ更新）、棚状態の取得は同時に 1 本までにし、確認中に来た更新要求は 1 回分だけ予約して完了後に取り直すようにする。操作の直後には必ず最新の状態が表示されることを保つ。

## スコープ

- 対象: `src/bunri/web/templates/index.html.j2`（JS のみ）、`tests/test_web_page.py`
- 対象外: サーバー側 API の変更、棚状態の問い合わせ自体の高速化、曲一覧やジョブの更新契機の変更、README の更新（更新契機の説明は現状 README に無い）

## 方針

1. 更新契機
   - 棚状態（`/api/pocket/status`）を取り直す契機は次に限定する: (a) ページを開いたとき、(b) 手動の「状態を再読込」、(c) 1 曲アップロード・全曲アップロード・棚削除（複合削除）の完了、(d) ローカルだけの削除の完了（棚から削除しなくてもローカル曲が「棚にのみある曲」へ移るため）、(e) 分離ジョブの完了（曲や楽器が増えて「未同期」に変わるため）。
   - タブ復帰（`visibilitychange` で visible になったとき）では曲一覧（`/api/songs`、`/api/songs-legacy`）とジョブ（`/api/pocket/job`）だけ更新し、棚状態は取り直さない。ただし、その曲一覧の更新で分離ジョブや Pocket ジョブの完了を新たに検知した場合は、(c)(e) の契機として棚状態を取り直す（現状の `refreshSongs` 内の判定を維持）。
   - タブ復帰時は曲一覧の更新(`refreshSongs`)とジョブの更新(`refreshPocketJob`)が並行して動く。全曲アップロードのように曲一覧に実行中の Pocket ジョブが現れない場合、`refreshPocketJob` の方が先に「追跡中のジョブ(`activePocketJobId` が設定済み)が完了または失敗に変わった」ことを受け取ることがある。この場合も (c) の契機として、曲一覧側と同じ共通の取得・予約処理へ渡す。追跡中でない過去の完了ジョブを再表示するだけの復帰では取り直さない。
2. 同時実行の抑止と予約
   - 棚状態の取得は同時に 1 本まで。確認中に (b)〜(e) の契機が来たら新しい要求は出さず、「取り直し」を 1 回分だけ予約する（何回来ても次の 1 回にまとめる）。
   - 予約した時点で、進行中の応答は古い可能性があるため無効化し、画面には反映しない（既存の世代カウンタを進めて無視する）。
   - 通信の終了処理（確認中フラグの解除、ボタンの復元、経過秒タイマーの停止、予約の処理）は、応答が古いかどうかに関係なく、通信の成功・失敗の両方で必ず行う。「古い応答を画面に反映しない」と「通信終了時の後処理」を分け、現状の `finally` が世代不一致で何もせず戻る構造を改める。
   - 終了時に予約があれば、次の 1 回を開始する。その再取得中にさらに操作が完了した場合も同じ規則で次の 1 回を予約する。
   - 手動の「状態を再読込」ボタンは確認中は無効のままとし、確認中に押せない現状を維持する。
3. 表示
   - 確認中の表示（ボタンの「再読込中…」とスピナー、件数文言の経過秒、完了時刻・失敗表示）は現状どおり。予約による再取得も通常の確認中として表示する。経過秒は再取得の開始時に 0 から数え直す。
4. Pocket 未接続時は現状どおり棚状態を扱わない。

## 完了条件・受け入れ基準

- [ ] タブを非表示にして戻したとき、新たなジョブ完了を検知しない場合は `/api/pocket/status` が呼ばれず、`/api/songs` と `/api/pocket/job` は呼ばれる
- [ ] タブ復帰時の曲一覧更新で分離ジョブの完了を検知した場合は、棚状態が取り直される
- [ ] 全曲アップロードの追跡中にタブを隠し、非表示の間に完了した状態で戻したとき、`/api/pocket/job` の応答が `/api/songs` より先に到着しても棚状態が取り直される(応答順序を制御したテストで検証する)。追跡中でない過去の完了ジョブを表示するだけの復帰では `/api/pocket/status` は呼ばれない
- [ ] 棚状態の確認中に、ローカル削除の完了・分離の完了・アップロードの完了の契機が複数回来ても、同時に飛ぶ `/api/pocket/status` は 1 本で、進行中の応答の終了後に 1 回だけ取り直される
- [ ] 確認中に棚削除またはローカル削除が完了した場合、削除完了 → 旧応答を解放して破棄（画面に反映しない）→ 次の取得で削除後の状態を表示、の順序で最終的に削除後の状態になる（既存テストの意図を維持し、並列通信を前提にしない形に更新する）
- [ ] 進行中の通信が失敗（通信エラーや HTTP エラー）で終わった場合も、確認中フラグが解除され、ボタンが復元され、予約があれば取り直しが開始される
- [ ] 予約による再取得中に新しい操作が完了した場合、さらに 1 回だけ予約される（2 回以上まとめて飛ばない）
- [ ] 確認中の表示（スピナー、経過秒、完了時刻、失敗表示）の既存テストが変更なしで通る
- [ ] 既存テストの意図を変えずに `uv run pytest -q -n auto` が全件成功する（Playwright Chromium がある環境で実行）
- [ ] `git diff --check` に警告が無い
- [ ] 作業ブランチへ commit 済み。変更対象（`src/bunri/web/templates/index.html.j2`、`tests/test_web_page.py`、計画書 2 ファイル）を明示して staging する
