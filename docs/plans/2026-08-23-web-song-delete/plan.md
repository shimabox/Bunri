# Web UI 曲単位削除機能 実装計画

- 日付: 2026-08-23
- ブランチ: `plan/2026-08-23-web-song-delete`
- 実装担当(駒): Sol medium（`codex exec`。確定済みの設計に沿って実装とテストを着実に完了する役割）
- 実装レビュー: Sol high（パス安全性、排他、失敗時の整合性、Web UI の操作性を重点的に確認する）

## 背景・目的

現行 Web UI は、同じ入力 digest のジョブを `Song` としてまとめて一覧表示できるが、不要になった曲と関連データを UI から安全に削除する手段がない。曲 ID を基準とした削除 API と確認ダイアログを追加し、処理中のデータや他の曲が共有するデータを壊さず、パッケージ・履歴・ログ・不要な共有物を一括削除できるようにする。新しい永続状態は追加せず、既存の `JobStore` ロックとジョブ状態を削除の排他制御にも使う。

## スコープ

### やること

- `DELETE /api/songs/{song_id}` を追加する
- 同じ digest に属する全ジョブを削除単位として扱う
- 対象ジョブの検証済み `package` が示すパッケージフォルダを安全に削除する
- 対象ジョブのログ、PID sidecar、JSON 記録を削除する
- 他ジョブが同じ相対パスを参照しないアップロード元を削除する
- 他ジョブが同じ digest prefix を使わない分離キャッシュを削除する
- `queued` または `running` のジョブを1件でも含む曲を `409 Conflict` にする
- 他の曲が同じパッケージフォルダを参照する場合も、何も削除せず `409 Conflict` にする
- `src/bunri/safepath.py` に symlink を辿らない削除用の検証・削除処理を追加する
- 曲カードを開いた展開領域の末尾に削除ボタンを置き、`<dialog>` と素の JavaScript で確認 UI を実装する
- API、`JobStore`、パス安全性、Playwright のテストを追加する
- `README.md` の Web UI 説明へ削除機能、削除対象、処理中は削除不可であること、不可逆操作であることを追記する

### やらないこと

- CLI への削除コマンド追加、および CLI 出力の削除
- 実行中ジョブのキャンセルや強制終了
- 複数ワーカー・複数サーバープロセス間の排他制御
- 認証・権限管理
- ゴミ箱、復元、Undo
- 曲や楽器単位の部分削除
- ジョブ状態への `deleting` 追加
- 隔離済みの `.json.bad-*` 記録から削除対象や共有参照を推測すること、および同記録の削除
- ジョブに紐づかない孤立アップロードを digest glob などで推測して削除すること
- 確認画面へのパッケージフォルダ名の表示

## 方針

### API とロック境界

`src/bunri/web/jobs.py` に曲単位の削除操作を集約し、`src/bunri/web/app.py` は結果を HTTP ステータスへ変換するだけにする。

削除対象の確定からメモリ上の除外まで、既存の `JobStore._lock`（`RLock`）を保持する。これにより、ワーカーの `queued -> running` 遷移や同じ digest の新規ジョブ作成と競合させず、削除専用の永続状態や tombstone を増やさない。複数プロセス間の排他は扱わず、現行の単一ローカルサーバー前提を維持する。

対象判定には `/api/songs` が返す最新ターゲットだけでなく、`song_id(job.digest)` が一致する全ジョブを使う。古いリトライ記録に `queued` / `running` が残っている場合も削除を拒否する。

API の応答は次で固定する。

- `204 No Content`: 削除完了
- `404 Not Found`: 対応する読み込み済みジョブがない
- `409 Conflict`: 対象に `queued` / `running` がある、またはパッケージフォルダが別の曲と競合する
- `500 Internal Server Error`: パス安全性の拒否やファイル削除失敗
- 既知の曲で一部ファイルが既に存在しない場合は削除済みとして扱い、`204` にする
- 成功後に同じ DELETE を繰り返した場合は、ジョブ記録がないため `404` にする

既存 middleware は `DELETE` を unsafe method として既に扱っているため、Origin 検証ロジック自体は変更しない。エンドポイント追加後、DELETE にも同一オリジン検証が適用されることを回帰テストで固定する。

### 削除対象の導出

保存されたパスをそのまま削除命令として使用せず、次の規則で候補を導出する。

- ジョブ JSON: 検証済みのジョブ ID から `web/jobs/<id>.json` を導出する
- ログ: ジョブ ID から既存の `_log_relpath()` を使って `web/logs/<id>.log` を導出する
- PID sidecar: 上記ログから `<id>.pid` を導出する
- パッケージ:
  - 対象ジョブのうち `job.package` があるものだけを使い、既存の `_validate_job_record()` を通過した `<dir>/<dir>.<target>.player.html` から `Path(job.package).parent` をパッケージ候補にする
  - 対象ジョブの `job.package` がない場合は `safe_filename(job.title)` からフォルダを推測せず、そのジョブについてはパッケージ削除を行わない。ジョブ JSON、ログ、PID sidecar など他の削除対象は通常どおり扱う
  - 同一 digest に複数フォルダが残る legacy 記録を考慮し、検証済み `package` を持つ全対象ジョブから一意なフォルダ集合を作る
  - 残存ジョブとの競合判定では、`job.package` がある場合はその親を使い、ない場合は保護側に倒して `safe_filename(job.title)` からフォルダを推測する。同じフォルダに当たる場合は、部分的に残さず削除全体を `409` にする
- アップロード元:
  - 対象ジョブの検証済み `upload` 相対パスを候補にする
  - 残存ジョブに同じ相対パスが1件でもあれば保存する
  - ジョブに紐づかない孤立アップロードは削除候補に含めず、digest glob は行わない
- キャッシュ:
  - digest が小文字16進40桁の SHA-1 形式の場合だけ `.cache/<digest先頭12桁>` を候補にする
  - 残存ジョブに同じ12桁 prefix があれば保存する
  - 非標準の legacy digest からキャッシュパスを推測しない
- 隔離記録: `.json.bad-*` は信頼せず、削除も参照判定も行わない

### パス安全性と失敗時の整合性

`src/bunri/safepath.py` に、削除前検証とファイル・ディレクトリ削除の共通 helper を追加する。

- `out_dir` 自体だけを resolve し、削除候補はそこからのリテラルな構成要素として検証する
- `web/jobs`、`web/logs`、`web/uploads`、`.cache`、パッケージ直下の固定親が実際に `out_dir` 内にあることを確認する
- 削除のために不足ディレクトリを新規作成しない
- `lstat` 相当で最終要素の symlink を検出し、リンク自体の削除にも進まず拒否する
- 期待する種類がファイルかディレクトリかを確認し、FIFO、device、種類不一致を拒否する
- ディレクトリ再帰削除では、内部の symlink はリンク先を辿らずリンクだけを除去する
- 存在しない候補は削除済みとして扱う
- 全候補を事前検証してから、最初の削除を始める
- 実削除直前にも安全条件を再確認する

削除順は、パッケージ、ログ・sidecar、非共有アップロード、非共有キャッシュ、ジョブ JSON、メモリ上の `_jobs` の順とする。ジョブ JSON を最後まで残すことで、途中の I/O エラーでは一覧と再試行手段を維持する。ファイルシステム全体を跨ぐ原子的削除や rollback は行わず、不足ファイルを許容する冪等な再試行で回復する。

### Web UI

削除ボタンは曲カードを開いた展開領域の末尾に置く。見出し行全体が既に開閉用 `<button>` であるため、見出しへ別ボタンを追加して DOM やキーボード操作を複雑にしない。

- `queued` / `running` を含む曲では削除ボタンを disabled にする
- ダイアログには曲名、表示中の楽器数と楽器名、および練習パッケージ・全ジョブ履歴・ログ・未共有のアップロード元とキャッシュが削除される旨を表示する
- legacy では複数フォルダがあり得て、現行 Song API に単一の正規フォルダ名がないため、フォルダ名は表示しない
- 操作は「キャンセル」「削除する」とする
- 送信中は確認・キャンセルを無効化し、確認ボタンを「削除中…」に変更する
- 送信中の Escape/cancel を抑止し、多重 DELETE を防ぐ
- API エラーはダイアログ内に表示し、操作可能状態へ戻す
- 成功時はダイアログを閉じ、`songExpandedStates[song.id]` を削除してから一覧を再取得する
- 成功後のフォーカスは曲一覧見出しへ移す
- キャンセル時は、ポーリングでカードが再生成されていても同じ曲の削除ボタンへフォーカスを戻す
- 新しい曲別の「削除中」状態は持たず、単一ダイアログの対象曲と送信中フラグだけを管理する

Song API に削除専用フィールドは追加しない。既存の `id`、`title`、`targets`、各 target の `status` / `target_label` だけで UI を構成する。

### テスト方針

`tests/test_web_jobs.py` では `JobStore` の公開削除操作を中心に検証する。

- 同一 digest の複数ターゲット、過去の失敗・再試行記録をまとめて削除
- legacy の複数パッケージフォルダを削除
- `package` がない失敗ジョブだけの曲を削除しても、同名の `out/<曲名>/` を削除しない
- `queued` / `running` がある場合は全対象が不変
- 残存ジョブと共有するアップロード・キャッシュを保存
- 同じ12桁 prefix を持つ異なる SHA-1 digest のキャッシュを保存
- 非標準 digest ではキャッシュを推測しない
- 残存ジョブの `package` がない場合も曲名から保護対象フォルダを推測し、パッケージフォルダ競合を `409` 相当として何も削除しない
- 最終要素または固定親の symlink を拒否し、リンク先とジョブ記録を維持
- パッケージ内部の symlink を辿らず、外部ファイルを維持
- 不足ファイルを許容
- JSON を最後に削除し、成功後だけメモリから除外
- 隔離済み `.bad-*` 記録を維持

`tests/test_web_api.py` では HTTP 契約を検証する。

- `204`、`404`、active の `409`、共有パッケージの `409`
- 削除失敗時の `500`
- 成功後に `/api/songs` と `/api/jobs` から対象が消える
- 同一オリジン・Origin なしは許可
- hostile origin、cross-port、壊れた Origin は `403` で、副作用がない

`tests/test_web_page.py` では Playwright で次を検証する。Playwright は skip せず、実行して成功させる。

- active 曲の削除ボタンが disabled
- 完了曲を開いて削除ボタンからダイアログを表示
- 曲名、楽器数・楽器名、削除概要の表示
- キャンセルで曲が残り、フォーカスが戻る
- 確定中の多重送信防止
- API エラーがダイアログ内に表示され、再操作できる
- 成功後にダイアログが閉じ、曲が一覧から消え、空表示へ更新される

対象テストを実装中の主なフィードバックループとし、約10分かかる全スイートは最後に1回実行する。
