# 実装依頼: Web UI 曲単位削除機能

## 背景

同じ入力 digest のジョブを `Song` としてまとめる現行 Web UI に、曲と関連データを安全に一括削除する機能を追加する。処理中のデータや他の曲が共有するデータを壊さず、削除失敗時にはジョブ記録を残して再試行できる設計とする。

## 対象

- リポジトリ: `shimabox/Bunri`
- ベースブランチ: `main`（参考。起点は次の SHA）
- ベース SHA: `804d116ebd4a9db156424fb9d3a90bc80462eab9`（`git switch -c plan/2026-08-23-web-song-delete 804d116ebd4a9db156424fb9d3a90bc80462eab9` を実行し、必ずこの SHA から作業ブランチを作る。ブランチ名を起点にしない）
- バージョン: `v0.3.0`
- 作業ブランチ: `plan/2026-08-23-web-song-delete`
- 実装担当: Sol medium（`codex exec`）
- 実装レビュー: Sol high

Python 3.13 を使用する。依存関係は `uv sync --frozen --extra web`、Playwright Chromium は必要に応じて `uv run playwright install chromium` で準備する。専用の lint / typecheck コマンドはない。

## タスク(この順で)

1. 作業ブランチを準備する。
   - `git switch -c plan/2026-08-23-web-song-delete 804d116ebd4a9db156424fb9d3a90bc80462eab9` で、指定 SHA から作成する。
   - 実装前に既存の `JobStore`、ジョブ記録検証、`song_id()`、Origin middleware、Song UI とテスト fixture を確認する。

2. `src/bunri/safepath.py` に削除用の共通 helper を追加し、削除候補の事前検証と symlink 非追従のファイル・ディレクトリ削除を実装する。
   - `out_dir` 自体だけを resolve し、候補は `out_dir` からのリテラルな構成要素として検証する。
   - `web/jobs`、`web/logs`、`web/uploads`、`.cache`、パッケージ直下の固定親が実際に `out_dir` 内にあることを確認する。
   - 削除のために不足ディレクトリを作らない。存在しない候補は削除済みとして扱う。
   - `lstat` 相当で最終要素の symlink を検出し、リンク自体も削除せず拒否する。
   - ファイル・ディレクトリの期待種類を確認し、FIFO、device、種類不一致を拒否する。
   - 再帰削除中に見つかる内部 symlink はリンク先を辿らず、リンクだけを除去する。
   - 全候補を最初の削除前に検証し、実削除直前にも安全条件を再確認する。

3. `src/bunri/web/jobs.py` に曲単位の公開削除操作と必要な競合エラーを追加する。
   - `song_id(job.digest)` が指定曲 ID と一致する読み込み済みの全ジョブを対象にする。Song API の最新ターゲットだけで判断しない。
   - 対象確定からファイル削除、成功後のメモリ上の `_jobs` 除外まで、既存の `JobStore._lock`（`RLock`）を保持する。新しい `deleting` 状態や tombstone は追加しない。
   - 対象がなければ not found とする。対象に `queued` / `running` が1件でもあれば、何も変更せず conflict とする。
   - 保存されたパスをそのまま削除命令に使わず、次の規則で削除候補を導出する。
     - ジョブ JSON は検証済みジョブ ID から `web/jobs/<id>.json` を導出する。
     - ログは既存の `_log_relpath()` で `web/logs/<id>.log` を導出し、PID sidecar はそのログから `<id>.pid` を導出する。
     - 対象ジョブのうち `job.package` があるものだけを使い、既存の `_validate_job_record()` を通過した `<dir>/<dir>.<target>.player.html` から `Path(job.package).parent` をパッケージ候補にする。
     - 対象ジョブの `job.package` がない場合は `safe_filename(job.title)` からフォルダを推測せず、そのジョブについてはパッケージ削除を行わない。ジョブ JSON、ログ、PID sidecar など他の削除対象は通常どおり扱う。
     - legacy の複数フォルダを考慮し、検証済み `package` を持つ対象ジョブから一意なパッケージフォルダ集合を作る。別の曲との競合判定では、残存ジョブの `package` がある場合はその親を使い、ない場合は保護側に倒して `safe_filename(job.title)` からフォルダを推測する。同じフォルダに当たる場合は、何も削除せず conflict とする。
     - 対象ジョブの検証済み `upload` 相対パスだけをアップロード候補にし、残存ジョブが同じ相対パスを参照する場合は保存する。ジョブに紐づかない孤立アップロードは削除せず、digest glob もしない。
     - digest が小文字16進40桁の SHA-1 形式の場合だけ `.cache/<digest先頭12桁>` を候補にし、残存ジョブに同じ12桁 prefix があれば保存する。非標準 legacy digest からキャッシュパスを推測しない。
     - `.json.bad-*` の隔離記録は削除にも共有参照判定にも使わない。CLI 出力を直接推測して削除・共有判定せず、対象ジョブの `package` がない場合も曲名から同名フォルダを削除対象にしない。
   - 全候補の検証完了後、パッケージ、ログ・PID sidecar、非共有アップロード、非共有キャッシュ、ジョブ JSON、メモリ上の `_jobs` の順で削除する。
   - 一部ファイルの欠損は許容する。I/O エラー時にファイルシステム横断の rollback は行わず、ジョブ JSON を最後まで残すことで一覧と冪等な再試行手段を維持する。メモリからの除外は成功後だけ行う。
   - 複数プロセス間の排他は実装しない。現行の単一ローカルサーバー前提を維持する。

4. `tests/test_web_jobs.py` に `JobStore` の公開削除操作とパス安全性のテストを追加する。
   - 同一 digest の複数ターゲットと、過去の失敗・再試行記録をまとめて削除できること。
   - legacy の複数パッケージフォルダを削除できること。
   - `package` がない失敗ジョブだけの曲を削除しても、同名の `out/<曲名>/` を削除しないこと。
   - `queued` / `running` がある場合は全対象が不変であること。
   - 残存ジョブと共有するアップロード・キャッシュを保存すること。
   - 異なる SHA-1 digest が同じ12桁 prefix を持つ場合にキャッシュを保存すること。
   - 非標準 digest ではキャッシュを推測しないこと。
   - 残存ジョブの `package` がない場合も曲名から保護対象フォルダを推測し、別の曲とのパッケージフォルダ競合を conflict として何も削除しないこと。
   - 最終要素または固定親の symlink を拒否し、リンク先とジョブ記録を維持すること。
   - パッケージ内部の symlink を辿らず、外部ファイルを維持すること。
   - 不足ファイルを許容すること。
   - 途中失敗時も JSON が残り、JSON を最後に削除して成功後だけメモリから除外すること。
   - 隔離済み `.bad-*` 記録を維持すること。

5. `src/bunri/web/app.py` に `DELETE /api/songs/{song_id}` を追加し、`JobStore` の結果を HTTP 契約へ変換する。
   - 成功は本文なしの `204 No Content`。
   - 対応する読み込み済みジョブがなければ `404 Not Found`。
   - active ジョブまたは共有パッケージフォルダの競合は `409 Conflict`。
   - パス安全性の拒否やファイル削除失敗は `500 Internal Server Error`。
   - 既知の曲で一部ファイルが既になくても `204`。成功後に同じ DELETE を繰り返した場合は `404`。
   - 既存 Origin middleware は変更しない。DELETE が unsafe method として既存検証を通る構成を使う。

6. `tests/test_web_api.py` に API 契約と Origin の回帰テストを追加する。
   - `204`、`404`、active の `409`、共有パッケージの `409`、削除失敗の `500` を検証する。
   - 成功後に `/api/songs` と `/api/jobs` から対象が消えることを検証する。
   - 同一オリジンと Origin なしは許可する。
   - hostile origin、cross-port、壊れた Origin は、副作用なしの `403` とする。

7. `src/bunri/web/templates/index.html.j2` に削除 UI を実装する。
   - 削除ボタンは曲カードを開いた展開領域の末尾に置き、見出し行には追加しない。
   - 既存 Song API の `id`、`title`、`targets`、各 target の `status` / `target_label` だけで UI を構成し、削除専用フィールドは追加しない。
   - `queued` / `running` を含む曲では削除ボタンを disabled にする。
   - 素の JavaScript と `<dialog>` を使用し、曲名、表示中の楽器数・楽器名、練習パッケージ・全ジョブ履歴・ログ・未共有のアップロード元とキャッシュが削除される旨を表示する。フォルダ名は表示しない。
   - 操作は「キャンセル」「削除する」とする。送信中は両操作を無効化し、確認ボタンを「削除中…」に変更し、Escape/cancel を抑止して多重 DELETE を防ぐ。
   - API エラーはダイアログ内に表示し、再操作できる状態へ戻す。
   - 成功時はダイアログを閉じ、`songExpandedStates[song.id]` を削除してから一覧を再取得し、曲一覧見出しへフォーカスを移す。
   - キャンセル時は、ポーリングでカードが再生成されていても、同じ曲の削除ボタンへフォーカスを戻す。
   - 曲別の「削除中」状態は追加せず、単一ダイアログの対象曲と送信中フラグだけを管理する。

8. `tests/test_web_page.py` に Playwright テストを追加する。
   - active 曲の削除ボタンが disabled になること。
   - 完了曲を開き、展開領域末尾の削除ボタンからダイアログを表示できること。
   - 曲名、楽器数・楽器名、削除概要が表示され、フォルダ名を前提にしないこと。
   - キャンセルで曲が残り、同じ曲の削除ボタンへフォーカスが戻ること。
   - 確定中の多重送信が防止されること。
   - API エラーがダイアログ内に表示され、再操作できること。
   - 成功後にダイアログが閉じ、曲が一覧から消え、空表示へ更新されること。
   - Playwright は skip せず、実際に実行して成功させること。

9. `README.md` の Web UI 説明へ、曲単位削除、削除されるデータ、`queued` / `running` を含む曲は削除できないこと、削除が不可逆であることを追記する。

10. 検証して commit する。
    - 実装中は対象テスト `uv run pytest -q tests/test_web_jobs.py tests/test_web_api.py tests/test_web_page.py` を中心に回す。
    - Playwright テストは skip で済ませず、Chromium を準備して成功させる。
    - 約10分かかる全スイート `uv run pytest -q` は、実装と対象テストが完了した最後に1回実行する。
    - symlink 非追従テストが macOS と Linux の双方で成立する実装・テストにする。既存 CI は Ubuntu、ffmpeg、uv 0.11.14、Playwright Chromium を使う。
    - 変更を機能単位で作業ブランチに commit する。複数 commit に分けてよい。
    - `docs/plans/` 配下は commit に含めない。`git add -A` は使わず、commit 対象の変更ファイルを明示して stage する。
    - push しない。
    - 最終 commit まで完了させてから終了する。

## 完了条件

## 未確定事項と判断の委ね方

- 勝手に決めてよい範囲: 既存の設計と命名規約に沿った helper・例外・内部変数の名前、テスト fixture の構成、責務を変えない範囲の小さなファイル内整理。
- 確定済みで変更しない範囲: 対象ジョブの検証済み `package` だけからパッケージ削除対象を導出し、`package` がない対象ジョブでは曲名から同名フォルダを推測しない。残存ジョブ側は `package` がなくても曲名から保護対象フォルダを推測する。孤立アップロードを消さない、CLI 出力と `.bad-*` に直接触らない、複数プロセス排他をスコープ外とする、確認画面にフォルダ名を出さない、既存 Song API に削除専用フィールドを追加しない。
- 止まって報告すべき範囲: 認証・キャンセル・復元・部分削除・プロセス間排他・完全な rollback・削除メタデータなどのスコープ追加、HTTP 契約や削除順の変更、既存挙動の破壊、新規依存の追加、安全条件を満たせない状況。
