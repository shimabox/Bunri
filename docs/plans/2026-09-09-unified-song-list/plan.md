## 背景・目的

Web UI の曲一覧は、Web からアップロードして分離したジョブ記録だけから組み立てられている。一方、Pocket への全曲アップロードや「出力先の全パッケージ N件中」の件数表示は出力先ディレクトリを直接走査するため、CLI で作ったパッケージは「一覧には出ないが同期され、件数には含まれる」状態になる。利用者から見ると曲数と件数が食い違い、CLI で作った曲を Web から削除することもできない。

この変更で、CLI で作ったパッケージも Web の曲一覧に通常のカードとして表示し、削除できるようにする。あわせて、パッケージの身元・パス検証をローカル表示・削除・Pocket 同期で共通化し、mp3 を持たない（wav のみの）パッケージや成果物が欠けたパッケージも安全に扱えるようにする。

## 方針

1. ローカルパッケージの共通検証を 2 層に分けて新設する
   - 層 1「身元・パスの安全性」: パッケージ名が安全（絶対パス・`.`・`..`・区切り文字を含まない、`.` 始まりでない、`web` / `.cache` / `.pocket` でない）、出力先直下の実ディレクトリ（symlink でない、解決後の親が出力先）、身元ファイル `.bunri-package.json` が実ファイル、メタデータの整合（`safe_name` がディレクトリ名と NFC 正規化で一致、`source` の digest と cache_key の整合、targets の形式）。結果は「取り込み可」「旧形式（身元ファイル無し）」「不正（理由の一覧）」を区別する。不正でも `source` が有効なら身元（digest、cache_key）を返し、競合判定に使えるようにする。
   - 層 2「成果物の充足」: メタデータの楽器×形式ごとに `<名前>.<楽器>.<形式>` と `<名前>.<楽器>.backing.<形式>`、プレイヤー `<名前>.<楽器>.player.html`、`<名前>.original.mp3` の有無と、実ファイルであること、空でないこと、読み取れることを列挙する。欠けていても例外にせず「何が有り、何が欠けているか」を返す。要求に応じてサイズと SHA-256 も計算できる。
   - 診断は集約して返し、最初の違反で打ち切らない。
   - Pocket の事前検査（`preflight`）は層 1 + 層 2 の結果に「全楽器の mp3（target と backing）と、`include_original=True` のとき `original.mp3` が揃っていること」を要求する形に再構成する。次の既存挙動を維持する: `include_original` の切替、メタデータ違反と不足ファイルの診断集約、未知楽器の報告（`allow_unknown_targets`）、mp3 が無い場合の `no_mp3` 分類、空・読取不能ファイルの拒否、資産ごとのサイズと SHA-256 の生成、`expected_digest` による身元照合。wav の存在は要求しない。
   - Web の曲一覧は層 1 + 層 2、Web の削除は層 1 だけを使う。成果物が欠けていても、身元とパスが確定できれば削除できる。
2. 曲一覧を統合する
   - ジョブ記録由来の曲と、出力先の全パッケージのうち層 1 で「取り込み可」となったものを、完全な音源 digest で統合する。曲 ID は従来どおり digest から導出し、Pocket 側の ID 対応を変えない。
   - `Song` に音源 digest とパッケージ名を持たせ、Pocket 連携（状態の対応付け、削除、同期）はジョブ記録ではなくこれを使う。
   - 楽器ごとの表示: 待機中・実行中・失敗はジョブ記録から。完了はメタデータと実ファイルから（ジョブ記録が無くても表示する）。生成中の楽器はメタデータから一時的に外れるため、ジョブ記録の状態を必ず残し、同じ楽器にジョブ記録と完了済みメタデータの両方がある場合はジョブ記録の状態を優先する。
   - 完了扱いの楽器は、実在する形式（mp3 / wav）のダウンロードリンクだけを出す。プレイヤーへのリンクはプレイヤー HTML が実在する場合だけ出す。メタデータにあるのに target と backing のいずれの形式も揃っていない楽器は「ファイル欠損」として表示し、プレイヤーとダウンロードのリンクを出さない。
   - API 応答では、ジョブ記録の無い楽器はジョブ ID を null にする。画面はジョブ ID に依存しない鍵（曲 ID + 楽器）でダウンロード欄の開閉状態を持つ。
   - 一覧の走査は `/api/songs` の応答時に行い、キャッシュは設けない（身元ファイルは小さく、既存の Pocket 対応付けでも同様の走査を行っている）。
3. 重複と衝突は競合として止める
   - 競合判定の対象は「層 1 で取り込み可となったパッケージ」に限らず、「メタデータに違反があっても有効な `source` を読めたフォルダ」も含める（コピーや改名で `safe_name` が不一致になった複製を見落とさないため。現行の Pocket 側と同じ扱い）。
   - 同じ完全 digest のフォルダが複数ある、または NFC 正規化で同名になるフォルダがある場合、その曲のカードに「同じ音源のパッケージが複数あります: A, B」と表示し、削除・再アップロード・Pocket 同期をすべて 409 で拒否する。どれかを勝手に選ばない。カードを統合しても、重複が解消された扱いにはしない。
4. 削除（`delete_song`）
   - 曲 ID を、ジョブ記録（従来どおり）とパッケージの身元（層 1）のどちらからでも解決する。
   - 削除対象の決め方は 2 経路を併用する。（a）従来経路: 検証済みの `job.package` を所有根拠とするパッケージディレクトリ。身元ファイルの無い旧 Web パッケージもこれで削除できる。（b）身元経路: 層 1 で確定したパッケージディレクトリ。`package` の無いジョブのタイトルから同名フォルダを推測して削除しない保護は維持する。
   - 存在する場合だけ、ジョブ記録・ログ・アップロード複製・他の曲と共有していないキャッシュも削除する。
   - 実行中または待機中のジョブがある曲、Pocket 操作が進行中の曲、方針 3 の競合、パッケージディレクトリを他の曲と共有している場合は従来どおり拒否する。
5. 複合削除（棚からも削除）の中断復旧
   - 「棚からも削除」は CLI 生成パッケージでも同じ経路で動く。削除ジョブには従来どおり song ID、digest、パッケージ名、接続先 fingerprint を保存する。
   - 棚削除の 204 を保存済みの削除ジョブは、分離ジョブの有無に関係なく、ジョブに保存した身元からローカル削除を再開する。身元ファイルが既に消えていても、保存したパッケージ名が層 1 のパス規則（安全な名前、出力先直下の実ディレクトリ）を満たせば残存ファイルを削除対象にする。パッケージ名がパス規則を満たさない、または symlink など安全に確定できない場合は削除せず競合として報告する。
   - 残存ファイルがある状態を「削除済み」の成功扱いにしない。
6. 同じ音源の再アップロード（`create_jobs` と `_resolve_title`）
   - ジョブの再利用やタイトル選択より前に、パッケージ側の競合検査（同一 digest の複数フォルダ、NFC 同名）と、身元一致フォルダの解決を行う。競合があれば 409 で拒否し、アップロード複製を残さない（既存の `SongDeleteConflict` と同じ扱い）。
   - ジョブが所有していないフォルダでも、身元情報の digest が一致すれば同じ曲として再利用し、`-2` を作らない。再利用するタイトルは、そのフォルダ名を導出するタイトル（メタデータの title）とし、`safe_filename(title)` がフォルダ名と一致することを確認する。一致しなければ再利用せず 409。
   - 同じ digest の既存ジョブがある場合も、そのタイトルから導く名前と身元一致フォルダの名前が食い違えば 409。
7. 旧パッケージの扱い
   - 身元ファイルの無いフォルダは、今回新たに取り込む対象からは除外する。曲一覧の下に「再生成が必要なパッケージ」としてフォルダ名を列挙する案内を出す（Pocket の legacy 扱いと同じ語彙）。既存のジョブ由来のカードには影響しない。
   - 層 1 で「不正」となったフォルダも取り込まないが、案内には理由を出さず名前だけを出す（秘密情報や環境のパスを画面に出さない）。
8. README の Web UI の節を更新する: CLI 生成パッケージも一覧に出ること、Web から削除できること、同じ音源を再アップロードすると同じフォルダに楽器が追加されること、身元ファイルの無い旧パッケージは案内に出ること、同じ音源のフォルダが複数ある場合は競合として操作が止まること。

## 完了条件・受け入れ基準

- [ ] CLI で作ったパッケージ（身元ファイルあり、ジョブ記録なし）だけの出力先で、`/api/songs` にその曲が返り、Web の一覧にカードが出て、楽器・プレイヤー・実在する形式のダウンロードが表示される
- [ ] wav のみのパッケージがカードに出て、mp3 のダウンロードリンクが出ない。同じパッケージの Pocket 状態は従来どおり mp3 が無い扱い（`no_mp3`）になる
- [ ] メタデータにあるが target と backing のファイルが無い楽器は「ファイル欠損」で表示され、プレイヤーとダウンロードのリンクが出ず、その曲を Web から削除できる
- [ ] ジョブが待機中・実行中・失敗の楽器は、メタデータの状態に関係なくジョブ記録の状態で表示される。生成中に一時的にメタデータから外れた楽器も「処理中」のまま表示される

- [ ] 身元ファイルの無い旧 Web パッケージ（ジョブ記録に `package` あり）は従来どおり削除できる。`package` の無いジョブのタイトルから同名フォルダを削除しない既存テストが変更なしで通る

## 公開経路

作業ブランチ `plan/2026-09-09-unified-song-list` に commit するまでが承認範囲。push、`main` への PR 作成、マージは別途判断する。自動デプロイは無い。CI は PR / push 時に `.github/workflows/ci.yml` が Ubuntu で `uv run playwright install --with-deps chromium` の後 `uv run pytest -q -n auto` を実行する。ローカルに Playwright Chromium が無い環境ではブラウザテストが skip されるため、検収は Chromium がある環境で行う。lint 相当は `git diff --check` であり、専用の lint / format / typecheck コマンドは無い。
