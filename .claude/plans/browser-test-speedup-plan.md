# ブラウザテスト高速化

作成: 2026-08-25。案 1 を 2026-08-29 に実施済み(下記「結果」参照)。案 2・3 は未着手、必要になったら再検討。

## 実施前の状況(計測)

- `tests/test_web_page.py` 13 件で約 4 分(アイドル時は約 2 分弱)。全 339 件は 8〜9 分。
- 遅いのは 4 件が 30 秒級: upload → プレイヤーリンクの一連 / 曲トグルの状態維持・フォーカス復元(ポーリング跨ぎ)/ 空 downloads で非表示。ダウンロードボタンのフォーカス復元が 18 秒。
- 原因は「ブラウザテストが直列」+「実時間で待つ」の掛け算:
  - 1 件ごとにサーバー起動 + Chromium 起動
  - ポーリング間隔 2 秒(`POLL_INTERVAL_MS`)を実時間で跨ぐ
  - fake runner の遅延と、runner スレッドの join(最大 10 秒)
  - マシンが高負荷のとき(他のブラウザテストや重い処理が同時に走る場合)は 2 倍以上に伸びる

## 案(効き目順)

### 1. pytest-xdist で並列化(第一候補・実施済み)

- `pytest-xdist` を dev 依存に追加し、`Makefile` の `make test` と CI の `uv run pytest -q` に `-n auto` を付ける。
- テストは `tmp_path` + 空きポートを `socket` で確保して個別サーバーを立てているので、並列に耐える見込み。ただし要確認:
  - 空きポート確保 → bind までの間に別ワーカーが同じポートを取る競合。リトライで対処すると、最初の bind 失敗時に lifespan 終了処理(`JobStore.shutdown()`)が走った app を再利用してしまいジョブが `queued` のまま動かなくなるため、テスト側で bind 済みソケットを `server.run(sockets=[...])` で渡し、競合の窓自体をなくす方針にした
  - Playwright の Chromium をワーカーごとに起動するメモリ(13 件同時なら数 GB。`-n 4` 程度に抑える選択肢)
  - 実時間待ちのテストは負荷でタイムアウトに近づく可能性(5〜6 秒のタイムアウトが詰まっているものは余裕を持たせる)
- 期待値: web テストの壁時計が「一番遅い 1 件」の 35 秒前後 + 起動オーバーヘッドまで縮む。全件も分離系の重いテストが並ぶぶん短縮。
- 受け入れ: ローカルで `uv run pytest -q tests/test_web_page.py -n auto` が 1.5 分以内、3 回連続で flaky なし。CI の所要時間が短くなっている。

### 2. 実時間待ちを短縮(第二候補、1 と併用可)

- ポーリング間隔をテストから短くできるようにする(例: サーバー起動時のオプションやクエリで `POLL_INTERVAL_MS` を上書き。本番既定は 2 秒のまま)。
- fake runner の遅延と join タイムアウトを、各テストが必要とする最小に見直す。
- 期待値: 30 秒級の 4 件が数秒に。1 と合わせれば web テスト全体で 1 分を切る。
- 注意: ポーリングの「間隔が短すぎてリクエストが重なる」経路を新たに踏まないか(ポーリング再スケジュールの既存ロジックを壊さない)。

### 3. Chromium をセッションで共有(第三候補)

- `sync_playwright` / `browser` を session スコープの fixture にし、テストごとは `context` だけ作る。起動コストを 1 回に。
- 効果は中程度。xdist と併用する場合はワーカーごとに 1 つになる。

## 結果(2026-08-29、案 1 のみ)

- 変更: dev 依存に `pytest-xdist` 追加、`make test` と CI を `pytest -q -n auto` に、`tests/test_web_page.py` の `_running_server` を bind 済みソケット渡しに変更。テスト本体・アサーションは未変更
- 実測(ローカル、`-n auto`): web テスト 13 件は 3 回連続で約 12 秒、全 340 件は約 31 秒。flaky なし
- 受け入れ基準(web テスト 1.5 分以内・3 回連続 flaky なし)を満たしたため、案 2・3 は保留

## 進め方

1. まず 1 だけ入れて計測(テスト本体は触らない)。flaky が出たら `-n` の上限で対処(ポート競合は bind 済みソケット渡しで解消済み)。
2. それでも 30 秒級が支配的なら 2 を入れる。
3. 3 は余力があれば。

## やらないこと

- テストの削減・skip 化(カバレッジは落とさない)。
- 本番のポーリング間隔の変更(テストから上書きできるようにするだけ)。
